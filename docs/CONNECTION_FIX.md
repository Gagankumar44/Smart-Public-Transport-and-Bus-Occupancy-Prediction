# API connection and missing-data fixes

The running API accepted connections but every measured endpoint, including health, timed out after 20 seconds. Its process had accumulated substantial CPU time under repeated polling. The application repeatedly loaded stop/route catalogs, concurrently rebuilt expensive schedule previews, lacked stop/clock indexes, and did not explicitly close several read connections. One failed Promise.all request also prevented otherwise successful catalogs from appearing.

Added stop and clock indexes to the validated active database and future imports; closed read connections; cached route catalogs by database version; coalesced schedule-preview requests with a ten-second TTL; moved static provenance reads outside the departure loop. Cached generated timestamps remain visible. The health endpoint runs independently of the synchronous request pool. API access logging is disabled for the active local server to avoid excessive console output.

The frontend now loads static catalogs separately, retains independently successful responses, prevents overlapping polls and pauses recurring updates in hidden tabs. Route search selects from its filtered catalog. Facilities renders at most 60 matching cards, with the full catalog searchable. Maps no longer create thousands of markers before a route is selected. Missing amenities or live measurements are not filled with guesses.

The archive's final valid Silk Board to Marathahalli forward departure was 22:25; the clock during diagnosis was later. Empty current results were therefore genuine schedule unavailability, separate from the connection fault. Journey Planner now accepts a timezone-aware future departure up to 30 days ahead in schedule mode, including a Tomorrow 08:30 shortcut. Date/calendar/direction checks still apply. Future previews do not create live watches or synthetic crowd forecasts and are not repeatedly polled.

Imported the archive's optional published fare tables, guarded by matching its SHA256 to the active version: 110 fare records and 170,161 fare rules. New GET /api/network/fares?origin=...&destination=... returns only exact zone/direction/route matches. The calculator uses these records instead of illustrative base/per-km pricing. Seven matching route options were returned for Silk Board to Marathahalli; the published fare was ₹35 per traveller and the UI calculated ₹70 for two. These are versioned published records, not guaranteed current ticket prices.

Verification: concurrent health/stops/routes/status/vehicle/journey checks changed from 20-second timeouts to under one second for the first benchmark, and 16–94 milliseconds on repeated requests. Proxy health returned in 94 ms, published fare lookup in 31 ms, and a cold future-trip search in 3.5 seconds. Sixty-two backend tests passed, including concurrent request coalescing, future-date calendar handling, invalid-time rejection and exact fare matching. Frontend lint, TypeScript and production checks are recorded in the final task result. One upstream Starlette/AnyIO warning remains.

Run `./Start-RushLess.ps1` from PowerShell for local startup after building. It starts hidden services with local log files and refuses to kill an unrelated or unresponsive port owner. Alternatively start uvicorn with `--no-access-log` on port 8001 and `npm run start` from frontend. No credentials are required for the local static-schedule API.

Live vehicle positions and measured occupancy still require an authorized provider. Supply provider documentation, an approved feed URL and usage permission; configure secrets locally in backend environment variables rather than sharing them in chat. No private endpoint was scraped and no live connection was fabricated.

The user confirmed that no authorized live provider is currently available. Public schedule/geometry/fares are therefore the active data paths; synthetic realtime fixtures remain isolated in automated tests. Browser checks confirmed the 500-F filtered route and its GTFS shape, 13 Bellanduru search matches, the ₹70 two-traveller published-fare total, and three valid journeys for 6 November 2026 at 08:30 IST. Future previews disable live watches and speculative crowd forecasts. The final optimized frontend build passed. The launcher was exercised from stopped services and successfully started both hidden processes; proxy checks then returned HTTP 200. Screenshot: [scheduled results](repaired-schedule.png).
